# Raziel v1.1 — The Self-Improving Loop (milestone definition)

**Status:** DEFINED 2026-09-05 (Geist, on Dillon's decision). Not yet planned, not yet built.
**Decision this rests on (Dillon, 2026-09-05):** do not describe Raziel as "self-improving" until a
closed loop inside the harness makes the word true. Build the loop; earn the word.
**Spec anchor:** `docs/SPEC.md` §3 (memory is a named engine component), §5 Lane 3 (life-OS is v2+;
v1 keeps only the *seams*). This milestone pulls ONE closed loop forward. It does not pull the lane.

---

## 1. What "self-improving" means here, and what it does not

**Means:** an outcome in session N produces a *scar* (a lesson with provenance); session N+1 loads
that scar; a decision in N+1 measurably differs from what N would have done; the diff is shown from
the event logs, not asserted.

**Does not mean, and is out of scope for v1.1 and later:**
- Raziel editing its own source, its own system prompt, or its own approval policy.
- Fine-tuning, weight updates, or any change to the model.
- Automatic rule-writing. An `/approve always` rule is a human act and stays one.

The bound is honest and should be stated wherever the word is used: *self-improving = the harness
reads its own past mistakes and behaves differently, with a visible audit trail.* Nothing more.

## 2. The frozen set — constraints outside the loop

A loop that can optimize its own gates will eventually optimize them away. These are **read-only to
the loop**, enforced in code, tested by a negative arm each:

| Frozen | Where it lives | Why |
|---|---|---|
| Approval policy ladder + risk classes | `src/approvals.ts`, `src/risk.ts` | the loop may *suggest*, never decide |
| Standing rules (`/approve always`) | `src/rules.ts` | rule-writing is a human act |
| Workspace confinement + symlink rules | `src/tools/workspace.ts` | M1b's hardest-won line |
| Tool surface per model profile | `src/profiles.ts` | lane-1 budget is data, not opinion |
| The session event log | `src/session.ts` | append-only; the loop reads it, never edits it |

A scar may contain the text "always allow X." The loop does not act on it. It is shown to the human.

## 3. Shape

```
session N ends ──► scar written to ~/.raziel/memory/<id>.md
                   (provenance: session id, event ids, taint inherited)
                          │
session N+1 boots ──► memory_load event (which scars, which hashes)
                          │
                   scars enter context as DATA with a provenance header,
                   not as instructions; the model reads them the way it reads a file
                          │
decision in N+1 ──► its tool_request / approval_request events are in the log,
                   so "what changed and why" is a diff of two logs
```

**Two new event types**, both in the session log so the Book renders them:
- `memory_write { scarId, sessionRef, eventRefs[], taint, hash }`
- `memory_load  { scarIds[], hashes[], bytes }`

**Taint propagates.** A scar derived from a turn that contained `tool_output` taint carries that
taint and renders with the same marker the transcript already uses. A scar is never more trusted
than the events it came from.

**Memory is capped.** A fixed byte budget per load, newest-first, with the cap and the eviction
visible in the `memory_load` event. The failure this prevents is the one this project's own
operators have lived: a standing list that grows by prepending and is re-derived by nobody.

## 4. The three halves, in order

**v1.1a — Capture (small; ships inside the dogfood window, before v1.0).**
- `/scar <text>` writes a scar file with provenance from the current session; the engine emits
  `memory_write`. An end-of-session prompt offers the same (deny-default; never auto-writes).
- No read side. Zero behavior change. Additive and opt-in, so it cannot endanger the v1.0 bar.
- **Why before v1.0:** the dogfood week is the only source of *real* scars. Without capture running
  during it, v1.1b's acceptance test has no corpus and gets satisfied with synthetic scars — which is
  the exact claim-before-truth failure the decision above rejects.

**v1.1b — Recall + the measured diff (the milestone proper; after v1.0).**
- `memory_load` at session start; scars in context as data with provenance headers; `/memory`
  lists what is loaded and why; `/forget <id>` evicts (human act, logged).
- Frozen-set negative arms (§2), one per row.
- **Acceptance (both required):**
  1. *Replay:* fixture session N (fake provider) yields a scar; fixture session N+1 with the same
     scripted provider but memory loaded produces a different `tool_request` sequence; the test
     asserts the diff and prints it.
  2. *Live:* one real scar, written during real use, shown to change one real decision in a later
     session. Two session ids, the scar id, and the two log excerpts go in the ship report.
     Synthetic scars do not satisfy this arm.

**v1.1c — Scar → skill (after v1.1b is measured).**
- A repeated scar becomes a reusable move: `~/.raziel/skills/<name>.md`, the mesh's `capture-skill`
  shape (problem → move → when-to-use), proposed by the harness, accepted by the human, loaded like a
  scar. The loop proposes; the human promotes.

## 5. Kill criterion (written before the spike, house doctrine)

If, **two weeks after v1.1b ships**, no real scar has changed a real decision (live arm unmet), the
feature is *memory*, not *self-improvement*. Keep the feature, drop the word, re-scope. The word is
earned by the live arm or not at all.

mistakes, and the life-OS lane (v2) inherits a memory module that has been measured rather than
imagined.
