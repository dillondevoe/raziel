## 1. The three things that actually matter

**A completed response is not evidence that usage was reported.** The pinned pi-ai adapter initializes a zero-filled usage object even when the server sends no usage. Copying every final object would produce false measurements. Its parser adds `reasoning` only when a usage object arrives, including an explicit all-zero report. This patch uses that distinction, with intercepted-response tests for absent, null, and all-zero usage. It does not re-parse SSE. Optional zero breakdowns are omitted because pi-ai cannot distinguish them from missing fields.

**A tool turn can contain several separately charged provider calls.** Engine now appends and yields one `usage` event per reporting `Provider.stream()` call, in both text-only and tool-enabled paths. Tool rounds retain the existing engine `turn` ID, with a distinct event ID per measurement. Counts are neither collapsed into one event per user message nor counted twice if a provider repeats its usage chunk. Attribution records the live provider instance's name and Engine's selected model.

**The display is a known subtotal, not a billing meter.** Book renders each measurement, including optional breakdowns when available. The statusline shows `known tokens N`, restored from the session log on boot and resume, accumulated from live events, and preserved across model swaps. It displays no token number before the first measurement. Unreported turns add nothing; they are not treated as measured zero. This enables accounting, but establishes no token saving or reduction in a subscription pool.

## 2. The plan, implemented

1. **Add the usage contract and persistence path.** `src/provider.ts` adds `TokenUsage` and a single final-snapshot stream chunk. `src/events.ts` adds the requested session-event variant and nonnegative safe-integer field validation. `src/engine.ts` owns event creation and ordinary append-before-yield persistence; `src/engine_tools.ts` invokes the same callback per provider round. FakeProvider accepts an optional per-call usage script; its default remains non-reporting. **Effect:** a reporting call becomes auditable from replay without putting usage metadata into model context. **Verification:** reporting/non-reporting fake tests cover both Engine paths, all eight bounded tool rounds, duplicate chunks, later errors, replay, and usage-append failure. **Risk:** failure to persist usage stops the turn before further tool work, matching ordinary audit-record failure behavior. **Size:** five production files, about 35 added lines.

2. **Map existing provider counters.** Anthropic uses the SDK's final accumulated message, compat uses pi-ai's parsed usage, and Ollama reads counts from its existing final NDJSON record. Ollama also flushes a final record without a trailing newline, which previously disappeared at EOF. **Effect:** measurements travel through the new channel without another parser or request. No expected model-token saving; one additional log record per reporting call. **Verification:** 15 intercepted-response tests cover cumulative updates, caches, reasoning, missing usage, real zeros, compat's request flag and fallback mapping, and fragmented Ollama records. **Risk:** compat's presence distinction depends on pinned pi-ai implementation details and must be checked on upgrades. **Size:** three production adapters, about 47 added lines.

3. **Connect Book and session totals.** Book renders usage directly, without requiring a later `turn_end`, and sanitizes provider/model strings. Status sums known counters, while TUI wiring loads replayed usage on startup/resume and routes live usage events. **Effect:** visible totals agree with the same persisted events an audit consumes. **Verification:** Book rendering and headless TUI tests cover absence, zero, cache/reasoning arithmetic, repaint requests, unmetered turns, model swaps, and session switches. **Risk:** the subtotal can be incomplete when a provider does not report or a stream is interrupted; the `known` label is deliberate. **Size:** four production files, about 38 added lines.

## 3. What I did not change, and why

**Frozen gates and log mechanics remain unchanged.** No changes to approvals, standing rules, risk classes, workspace confinement, profile tool surfaces, or `src/session.ts`. Event validation recognizes the additional type, but append/replay mechanics and old-event semantics are untouched. Usage follows ordinary audit persistence; the reviewed error and tool-result ordering remains intact.

**Profiles, transports, and dependencies remain unchanged.** The removed tool-bearing Chat Completions profile stays removed. No Responses-API provider, persona-path change, auth change, sampling change, or tool-schema change. No dependency, lockfile, pricing table, or wire parser was added. The compat usage request flag was already present through pi-ai; adding another override would not improve coverage.

**No retrospective estimates or budget enforcement.** Old logs remain unmetered. There is no tokenization of text, conversion of `contextTokens` into spend, context clipping, compaction, rate calculation, or subscription-dollar estimate. Provider token counts do not establish remaining weekly allowance. No monitoring or useful work was removed to claim a saving.

## 4. What I could not assess

**Live reporting and billing reconciliation were not exercised.** All new provider tests use intercepted responses, and the TUI test is headless. An authorized live request to each deployed endpoint, followed by replay and comparison with its account records, would establish reporting availability and billing agreement. Session/provider/model attribution is present; mapping a session to an external lane still requires the launcher's session-to-lane record.

**Interrupted calls can remain unmetered.** Existing cancellation suppresses further provider chunks. Anthropic publishes only after the SDK resolves its final message; an interrupted or failed stream may therefore have no usage event despite consuming tokens. Compat can publish parsed usage before a non-abort error when pi-ai supplies it. Engine retains any usage already delivered before a later error. No final total is inferred from a partial stream.

**The pinned compat parser does not preserve all wire-field presence.** Besides optional zero breakdowns, malformed partial usage objects can be defaulted by pi-ai, so this adapter assumes the API's required primary counters are present in a reported usage object. Exact validation of nonconforming endpoints would require pi-ai to expose field presence or raw parsed usage. The current no-usage test protects absent/null usage objects, not arbitrary malformed counter objects. Dependency upgrades should rerun those intercepted-response controls and inspect the parser before changing this assumption.
